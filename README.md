# ربات فروش اشتراک تلگرام — نسخه‌ی قابل اجرا روی Railway

این پوشه همان ربات (`bot.js`، بدون هیچ تغییری در منطق داخلی‌اش) را طوری
بسته‌بندی کرده که به‌جای Cloudflare Workers، روی **Railway** (یا هر هاست
Node.js دیگر) هم اجرا شود.

## ساختار فایل‌ها

| فایل | توضیح |
|---|---|
| `bot.js` | همان فایل اصلی ربات — کاملاً دست‌نخورده |
| `server.js` | یک سرور Node.js که درخواست‌های HTTP را می‌گیرد و به `bot.js` می‌دهد |
| `db.js` | جایگزین KV و D1 کلادفلر با یک فایل SQLite روی دیسک |
| `package.json` | وابستگی‌ها و دستور اجرا |
| `.env.example` | نمونه‌ی متغیرهای محیطی موردنیاز |

## ۱) بالابردن روی Railway

1. یک پروژه‌ی جدید در [railway.com](https://railway.com/) بسازید و
   «Deploy from GitHub repo» را انتخاب کنید (بعد از اینکه این پوشه را طبق
   بخش پایین در گیت‌هاب گذاشتید).
2. Railway به‌صورت خودکار Node.js را تشخیص می‌دهد، `npm install` را اجرا
   و با `npm start` (یعنی `node server.js`) بالا می‌آورد.
3. در تب **Variables** پروژه، متغیرهای محیطی را ست کنید (لیست کامل در
   `.env.example`). حداقل‌های لازم:
   - `TELEGRAM_BOT_TOKEN`
   - `ADMIN_IDS`
   - `PASARGUARD_BASE_URL`
   - `PASARGUARD_API_TOKEN` (یا `PASARGUARD_USERNAME` + `PASARGUARD_PASSWORD`)
   - `WEBHOOK_SECRET` (توصیه‌شده، برای امنیت وبهوک)
4. **مهم — ماندگاری داده‌ها:** در تب **Volumes** یک Volume جدید بسازید و
   آن را روی مسیر `/data` مانت کنید، و متغیر `DATA_DIR=/data` را هم اضافه
   کنید. اگر این کار را نکنید، با هر دیپلوی جدید، سفارش‌ها/کارت‌ها/کیف‌پول‌ها/
   سشن‌های در حال انجام از بین می‌روند (چون فایل SQLite داخل کانتینر است).
5. Railway یک دامنه‌ی عمومی به شما می‌دهد (Settings → Networking → Generate
   Domain). آن آدرس را در مرورگر باز کنید — صفحه‌ی اصلی ربات به‌صورت خودکار
   وبهوک تلگرام را روی همان آدرس تنظیم می‌کند (دقیقاً مثل نسخه‌ی کلادفلر).
6. اگر عضویت اجباری در کانال فعال است، یادتان نرود ربات را در کانال
   (`CHANNEL_ID`) ادمین کنید.

نیازی به دست‌زدن به Dockerfile یا تنظیمات build نیست؛ Railway با همین
`package.json` خودش می‌فهمد چه کار کند.

## ۲) گذاشتن روی گیت‌هاب

از داخل همین پوشه (جایی که `bot.js`, `server.js`, `package.json` هستند):

```bash
git init
git add .
git commit -m "ربات پارس وی‌پی‌ان - نسخه Railway"
git branch -M main
git remote add origin https://github.com/<username>/<repo-name>.git
git push -u origin main
```

فایل `.gitignore` از قبل تنظیم شده که `node_modules/`، فایل‌های SQLite
محلی، و `.env` واقعی هرگز به گیت‌هاب پوش نشوند (توکن‌ها و اطلاعات حساس
همیشه فقط در Variables خود Railway ست می‌شوند، نه داخل کد یا گیت‌هاب).

بعد از پوش اول، هر بار که در Railway «Deploy from GitHub» را وصل کنید،
با هر `git push` جدید، Railway خودش دوباره دیپلوی می‌کند.

## نکات فنی (برای اطلاع، نیازی به تغییر ندارید)

- `bot.js` اصلاً به Cloudflare وابسته نیست — فقط از دو چیز استفاده می‌کند:
  `env.SHOP_KV` (کلید/مقدار ساده) و `env.DB` (یک دیتابیس SQL با
  `prepare().bind().run()/.all()/.first()`؛ دقیقاً همان رابط Cloudflare D1).
  `db.js` همین دو رابط را با یک فایل SQLite واحد (`better-sqlite3`)
  شبیه‌سازی می‌کند — چون D1 هم خودش روی SQLite ساخته شده، هیچ کوئری‌ای در
  `bot.js` نیاز به تغییر نداشت.
- `server.js` هر درخواست HTTP خام Node.js را به یک `Request` استاندارد
  (همان Web API که Workers هم استفاده می‌کند) تبدیل می‌کند، به
  `bot.js`'s `fetch(request, env, ctx)` می‌دهد، و `Response` برگشتی را
  مستقیم به کلاینت می‌فرستد.
- چون Railway (برخلاف Cloudflare Workers) یک پردازه‌ی Node.js واحد و
  پایدار را اجرا می‌کند (نه یک isolate جدید به‌ازای هر درخواست)، مشکلاتی
  مثل گم‌شدن سشن بین درخواست‌ها اینجا اصلاً پیش نمی‌آید — و چون سشن‌ها را
  هم روی همان فایل SQLite ذخیره می‌کنیم، حتی با ری‌استارت/دیپلوی مجدد هم
  از بین نمی‌روند (به‌شرطی که Volume را طبق بخش ۱ وصل کرده باشید).
